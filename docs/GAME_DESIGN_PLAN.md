# 放置塔防遊戲規劃書（參考《The Tower - Idle Tower Defense》）

這份文件是本專案的整體規劃：先拆解參考作品的設計，再依序定義核心循環、系統、數值框架、技術架構與開發路線圖。

---

## 1. 參考作品拆解：The Tower 為什麼好玩

《The Tower》的畫面極簡（一座塔 + 圓點敵人），但留存極強，關鍵在於它把「放置(Idle)」和「塔防(TD)」疊出了**三層嵌套的成長循環**：

### 三層循環

| 循環 | 時間尺度 | 貨幣 | 內容 |
|------|----------|------|------|
| 戰鬥內循環 | 秒～分鐘 | Cash（現金） | 殺敵賺 Cash → 買**本場限定**升級 → 撐過更多波 → 死亡歸零 |
| 單場循環 | 分鐘～小時 | Coins（金幣） | 一場結束結算 Coins → 回到工坊買**永久**升級 → 下一場起點更強 |
| 長期 Meta 循環 | 天～月 | Gems、研究時間、模組素材 | 卡片、研究室、終極武器、模組、Tier 解鎖 → 改變玩法本身 |

**設計核心：每一場「失敗」都是有收穫的。** 死亡不是懲罰，而是把場內進度兌換成永久進度的結算點。這是放置塔防和傳統塔防最大的差異，也是規劃時最優先要做對的事。

### 參考作品的系統清單

- **戰鬥**：塔固定在畫面中央，敵人從四面八方湧入，塔自動索敵攻擊；波次(Wave)無限遞增。
- **場內升級（Cash，死亡歸零）**：分三類
  - 攻擊：傷害、攻速、暴擊率、暴擊倍率、射程、多重射擊、彈射…
  - 防禦：血量、回血、減傷%、荊棘反傷、擊退…
  - 經濟：每殺金額、每波金額、利息、免費升級機率…
- **工坊 Workshop（Coins，永久）**：與場內升級同構的永久版本，等級上限高、成本指數成長。
- **卡片 Cards（Gems）**：裝備制、有卡槽限制，提供構築(build)選擇。
- **研究室 Labs**：用「真實時間」跑的研究佇列，典型放置遊戲的長期掛機目標。
- **終極武器 Ultimate Weapons**：死亡波、黃金塔、黑洞、時間力場…徹底改變戰鬥節奏的大招。
- **模組 Modules**：帶稀有度的裝備 + 副詞條，後期深度養成坑。
- **Tier 制**：更高難度的平行關卡，取代傳統「重生(Prestige)」的角色。
- **錦標賽 / 活動**：週期性的社交競爭目標。

## 2. 我們的設計支柱（Design Pillars）

1. **每場必有收穫**：任何一場 run 結束都要拿到永久貨幣，數字要明顯感覺得到成長。
2. **前 5 分鐘就要爽**：第一場就能買到 3~5 次場內升級，看到殺敵效率肉眼可見變快。
3. **決策淺、深度後置**：前期只有「買哪個升級」一種決策；卡片/構築等深度系統分階段解鎖。
4. **離線也在玩**：關掉遊戲回來要有離線收益結算畫面（這是放置遊戲的招牌儀式感）。
5. **資料驅動**：所有數值放設定表，不寫死在程式裡，才能高速迭代平衡。

- [x] 敵人類型 3 種：普通、快速（血少速快）、坦克（血多速慢）

### 第二階段（M2）✅ 已完成

- [x] 速度切換（x1 / x2 / x3）
- [x] Boss 特殊能力（每 6 秒召喚小兵）、遠程敵人（狙擊手，射程外停下攻擊塔）

### 第三階段（Meta 層）

## 4. 數值設計框架

放置遊戲的本體其實是數值曲線。核心公式全部用「指數成長」：

```
升級成本(lv)   = baseCost × costGrowth^lv        （costGrowth ≈ 1.15~1.35）
升級效果(lv)   = baseValue + valuePerLevel × lv   （效果線性、成本指數 → 自然出現軟上限）
敵人血量(wave) = baseHp × hpGrowth^wave           （hpGrowth ≈ 1.07~1.12）
敵人數量(wave) = min(baseCount + wave × k, 上限)
Coins 結算     = Σ(每殺 coin) + 波次獎勵，約與到達波次呈超線性
```

平衡目標（拿碼表實測）：
- 第一場 run：3~5 分鐘死在 Wave 15~25。
- 買完第一輪工坊升級後：下一場多撐 30~50% 波數 —— **成長感的量化標準**。
- 每次卡關（波數成長 < 10%）時，工坊裡永遠有一個「存 2~3 場就買得起」的下一個目標。

**建議一開始就把數值表放進 Google Sheets / CSV，用公式模擬 50 場 run 的進度曲線，再匯出成 JSON 給遊戲讀。** 平衡是改表，不是改 code。

大數字：JS 的 Number 到 9e15 就會失真，放置遊戲一定會超過。方案：自寫 `{mantissa, exponent}` 結構或用 `break_infinity.js` 這類函式庫（比 BigInt 快，適合遊戲）。

## 5. 技術選型建議

| 方案 | 適合情況 | 備註 |
|------|----------|------|
| **Godot 4 (GDScript)** ✅ 推薦 | 目標是手機上架（參考作品就是手機遊戲） | 免費、輕量、2D 效能好、一鍵輸出 Android/iOS |
| **TypeScript + PixiJS（或 Phaser）** ✅ 推薦（快速起步） | 想先在網頁快速驗證玩法、部署到 itch.io / GitHub Pages | 迭代最快，之後玩法定了再移植 |
| Unity | 已熟悉 Unity、想用 C# | 對這種輕量 2D 專案偏重 |

這款遊戲美術極簡（幾何圖形就夠），瓶頸在**同屏幾百個敵人 + 子彈**的效能：
- 一律用物件池(Object Pool)，不要每發子彈 new 一個物件。
- 敵人索敵用距離平方比較（省開根號）；數量大時加空間網格(Spatial Grid)。
- **邏輯與渲染分離**：遊戲邏輯跑固定 tick（例如 20 tick/秒），渲染插值。這樣 x3 加速 = 每幀多跑幾個 tick，離線收益 = 快轉模擬或公式估算，都是同一套邏輯。

## 6. 程式架構

```
src/
  core/            # 純邏輯，不碰渲染 —— 可以獨立跑單元測試
    simulation.ts  # 固定 tick 的戰鬥模擬（生成、移動、索敵、傷害、死亡）
    economy.ts     # Cash/Coins 計算、升級成本與效果
    waves.ts       # 波次生成規則
    offline.ts     # 離線收益結算
  data/            # 全部數值設定（JSON，由試算表匯出）
    upgrades.json
    enemies.json
    waves.json
  meta/            # 工坊、（未來的）卡片、研究室
  save/            # 存檔序列化、版本遷移(migration)
  ui/              # 渲染與介面，只讀 core 的狀態
```

關鍵原則：
1. **core 不依賴引擎**。這讓你可以寫「自動模擬 1000 場」的平衡測試腳本。
2. **存檔從第一天就帶 `version` 欄位**，並寫好 migration 機制 —— 放置遊戲玩家的存檔就是他的全部資產，弄壞一次就流失一個玩家。
3. 存檔內容存「玩家的購買紀錄與貨幣」，不要存計算後的屬性值 —— 改平衡表後屬性要能重算。

## 8. 常見陷阱（先寫下來避免踩）

1. **一開始就做 Meta 系統** —— 戰鬥內循環不好玩，後面全白搭。先把 M0 打磨到爽。
2. **數值寫死在程式裡** —— 平衡迭代會慢到死。第一天就資料驅動。
3. **忽略離線收益的上限** —— 沒有折扣係數/時數上限，離線會比在線划算，玩家反而不玩了。常見做法：離線效率 50%，上限 8~24 小時，之後用研究升級延長（本身又是一個成長目標）。
4. **用浮點數直接存大數** —— 過 1e15 之後升級成本會出現「買了沒反應」的靈異 bug。
5. **成長曲線太平滑** —— 放置遊戲需要「卡關 → 攢錢 → 突破 → 暴爽」的節奏，刻意在曲線上放幾個門檻（新敵種、Boss 強化）逼玩家回工坊。
6. **第一場太難或太久** —— 前 3 分鐘沒有三次「變強」體驗，玩家就走了。
